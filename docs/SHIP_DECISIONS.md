## Product goal and priorities

The goal is a usable, high-quality Shellfox migration with the requested Electron functionality and pixel parity, not a terminal demo or perfect experimental proofs.

User priority is explicit and equal:
- Windows at home.
- Linux at work, including desktop and headless use.
- Android while away, including reconnecting to hosts and continuing work.

These are co-primary acceptance targets. A Windows-only build is not the usable-product milestone. Shared changes must stay consistent across them. Implementing on the available Windows machine does not establish Linux or Android acceptance.

Mac and iOS remain supported-scope obligations. Schedule their adapters and acceptance after the co-primary workflows are integrated; do not silently remove them or claim full supported-platform completion without their checks.

Preserve fixed approval policy: approved devices get Write/terminal control and explicit full host-account filesystem authority without elevation. Authentication, current approval, real leases, revocation and OS ACLs remain mandatory. Elevated/admin sources stay local-only unless the user explicitly changes that policy.

## Efficiency rules

1. Each task must name a requested feature, demonstrated defect or necessary integration/security/test gate. Otherwise park it.
2. Each task needs an observable stopping condition. Test counts and documents are evidence, not the product goal.
3. Prefer existing Host, Service, Runtime, transports, stores, journals and protocols. New infrastructure needs evidence that the existing mechanism cannot meet the requirement.
4. Batch related fixes, then perform one focused independent review of the stable high-risk implementation. Review only material deltas afterward.
5. Reopen a completed item only for a concrete finding. Distinguish an actual defect, missing evidence and an optional stronger guarantee.
6. Time-box investigation to half a working day normally. At most two days without a concrete result; then present concise options and a recommendation. Do not turn a missing proof into another subsystem by default.
7. No new contract revision, prototype, audit project or expanded test matrix unless it unblocks the active milestone.
8. Keep at most three active delivery lanes. Each file has one implementation owner; reviewers do not edit it. Coordinate Cargo/native test windows only where outputs or resource ownership overlap.
9. Do not weaken safety to make a test pass. Failed runs remain failures, cross-compiles are not runtime tests, and missing prerequisites are HOLDs.
10. Consult this file before accepting a new subagent proposal. Report milestones and remaining blockers, not a stream of acknowledgments. Message only workers whose next action changes; do not wake parked workers for FYI broadcasts.
